Proposal

Agentic SDLC with GitHub

A practical operating model for using AI coding agents safely at organizational scale. The goal is not maximum autonomy. The goal is faster delivery with stronger verification, clear ownership, and GitHub-enforced guardrails.

Core principle
Define intent, constrain the agent, verify the result, and preserve human accountability.

03 • GIT WORKFLOW

Prefer trunk-based development and small PRs

Recommended branch model

main
 │
 ├── feat/123-add-payment-validation
 ├── fix/456-null-reference
 └── refactor/789-order-service

Issue → short branch → small PR → merge → delete

Branches should usually live for hours or a few days, not weeks. Agentic workflows reduce the need for large, long-running branches.

PR size is a control mechanism

Prefer
  • Atomic change
  • One business purpose
  • Easy-to-review diff
  • Clear test evidence
  • Easy rollback
Avoid
  • Thousands of changed lines
  • Mixed feature + refactor + dependency update
  • Long-lived branches
  • Large generated diffs
  • Hard-to-explain history
Key idea: with AI, human attention becomes the scarce resource. Small PRs protect review quality.
04 • REPOSITORY DESIGN

The repository becomes the agent’s operating context

/ ├── AGENTS.md ├── README.md ├── CONTRIBUTING.md │ ├── .github/ │ ├── copilot-instructions.md │ ├── instructions/ │ │ ├── csharp.instructions.md │ │ ├── sql.instructions.md │ │ └── testing.instructions.md │ ├── skills/ │ │ ├── implement-feature/ │ │ ├── code-review/ │ │ └── database-change/ │ ├── CODEOWNERS │ ├── pull_request_template.md │ └── workflows/ │ ├── docs/ │ ├── architecture.md │ ├── testing.md │ └── security.md ├── src/ └── tests/

What belongs where

AAGENTS.md
Short, stable repository-wide rules and invariants shared across agents.
IPath instructions
Specific rules for C#, SQL, tests, infrastructure, security-sensitive folders, etc.
SSkills
Reusable workflows for common tasks such as implementation, review, schema changes, or releases.
DDocs
Architecture, testing strategy, security boundaries, operational expectations.
OCODEOWNERS
Automatic routing of sensitive changes to the right human owners.

Keep repository instructions compact

# Architecture
- Controllers must not contain business logic.
- Domain must not reference Infrastructure.
- External operations must be idempotent.

# Testing
- New business logic requires tests.
- Database behavior requires integration tests.
- Do not delete or disable tests to make CI pass.

# Git
- Never commit directly to main.
- Keep changes scoped to the assigned issue.
- Do not modify unrelated files.
- Do not add dependencies without justification.

Long “everything documents” become noisy. Stable global rules should stay short, while specialized instructions should live close to the files and workflows they govern.

05 • ENFORCEMENT

Move standards from prose into executable checks

Architecture

Rules → Architecture tests

Enforce dependency direction, bounded contexts, layering, naming conventions, or package boundaries automatically.

Code quality

Standards → Lint / format

Formatting, analyzers, compiler warnings and style should be machine-checkable and consistent.

Security

Policy → Scanning

Use SAST, CodeQL, dependency review, secret scanning and push protection as hard gates.

Testing

Behavior → Tests

Acceptance criteria should map to unit, integration and end-to-end tests where appropriate.

Dependencies

Supply chain → Review

New packages should be justified, reviewed, scanned and checked for maintenance and license risk.

CI

Definition of correct

Build, tests, architecture checks and security checks are the objective verification layer.

Rule of thumb: if a standard can be checked automatically, do not rely only on an instruction file or prompt to enforce it.
06 • REVIEW MODEL

Change what humans spend time reviewing

Automation / AI should handle more of

✓Formatting, lint and obvious style issues
✓Missing null checks and simple static-analysis findings
✓Basic test failures and build issues
✓Known architecture-policy violations
✓Security and dependency scanning

Humans should focus on

1Problem correctness
Does this solve the right problem?
2Architecture and design
Is the approach maintainable and consistent?
3Edge cases and business risk
Can this corrupt data or break important behavior?
4Security boundaries
Are authorization, data and trust boundaries correct?
5Tests and simplicity
Do tests prove behavior, and is this the simplest reasonable solution?
Operating model: AI review is an additional reviewer. CI is objective verification. Human review carries accountability.

08 • COMMIT HYGIENE

Use logical checkpoints, then squash for clean history

During agent work

feat(portfolio): add market value calculation
test(portfolio): cover currency conversion
refactor(portfolio): extract pricing service

Intermediate commits should be meaningful enough to support debugging, review and recovery.

On main

A  feat: calculate portfolio market value (#142)
B  fix: handle missing FX rate (#143)
C  feat: expose market value API (#144)

Squash merge is a good default for most application work. It keeps main readable without requiring perfect intermediate history.

09 • GOVERNANCE

Adopt an agent trust ladder

Autonomy should be earned
Level 0
AI suggests code
Human performs all repository actions.
Level 1
AI edits locally
Human commits and pushes.
Level 2
AI creates commits
Human pushes and reviews.
Level 3
AI creates branch + PR
Human approves.
Level 4
AI fixes CI and review findings
Human still approves merge.
Level 5
AI handles low-risk issues
Policy + CI + human oversight.
Level 6
AI auto-merges pre-approved low-risk work
Strict scope, policy and monitoring required.

Trust level should vary by repository and change type

Change typeSuggested posture
Docs / generated metadataHigher autonomy after validation
Routine application codeAgent creates PR; human approves
Financial calculationsHuman design + review required
Auth / authorizationSecurity owner required
Database migrationsOwner approval + rollback plan
CI / infra / deploymentPlatform owner + stricter policy
Important: “the agent can do it” is not the same as “the agent should have permission to do it.”

13 • MEASUREMENT

Measure successful change, not generated code

Lead TimeHow quickly work moves from approved intent to production.
PR Cycle TimeHow long changes wait for verification and review.
Deployment FrequencyHow often safe changes reach users.
Change Failure RateHow often releases cause incidents or rollback.
Escaped DefectsProblems that reach production.
Rework RateHow often agent-produced code needs significant correction.
CI Failure RateQuality of changes before merge.
Median PR SizeWhether review remains practical as throughput grows.
Avoid vanity metrics: lines of code, commits per developer, or number of AI-generated PRs can increase while system quality decreases.
14 • PROPOSED ROLLOUT

A safe path to organizational adoption

Phase 1 — Standardize repositories
Rulesets, branch protection, CODEOWNERS, PR template, CI baseline, AGENTS.md.
Phase 2 — Enable guided agent work
Agents can edit, commit, create branches and PRs. Human merge approval remains mandatory.
Phase 3 — Add reusable instructions and skills
Path-specific coding, testing, database and security guidance.
Phase 4 — Expand automated verification
Architecture tests, dependency checks, security scans, stronger integration coverage.
Phase 5 — Increase autonomy by risk class
Allow low-risk categories to progress further automatically while preserving strict controls for sensitive areas.

Minimum organizational standard

✓No direct pushes to protected branches
✓Required CI before merge
✓Human approval for production code
✓CODEOWNERS for high-risk areas
✓Small PR expectations
✓Repository-wide agent instructions
✓Security and dependency scanning
✓Traceability from issue to deployment
✓Outcome-based engineering metrics
15 • DECISION

Recommended policy statement

AI agents should be treated as high-throughput engineering participants operating inside enforced repository, CI, security, and review boundaries.

We should optimize for safe speed: clear intent, small changes, automated verification, least privilege, risk-based human review, clean Git history, and measurable outcomes. The objective is not to remove humans from the SDLC. It is to move human attention to the decisions where judgment and accountability matter most.
